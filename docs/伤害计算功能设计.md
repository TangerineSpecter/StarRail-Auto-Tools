## 公共机制数据基础（2026-09-15）

公共数据的统一契约位于 `src/shared/contracts/catalogue-rules.ts`，模板及准确数值曲线位于 `src/data/catalogue-mechanics.json`。`resolveAbility` 解析实际有效等级；`evaluateRules` 读取审核状态、来源指纹、解锁、环境、实体属性及可选事件，返回贡献、事件候选和未生效原因。缺失字段返回未知，不自动视为零。`validateCatalogueRules` 校验参数引用、表达式、单位及依赖循环。

本期事件求值仅解释条件和效果定义，不修改状态、资源或回合，不递归推进触发链。站街装备计算使用独立审阅的 ID 规则；伤害加成、易伤、防御无视、抗性穿透不得混入攻击力。显示在游戏属性面板与是否战斗生效是不同审核维度。

统一来源已加入客户端；完整战斗规则库的逐条审核仍需单独验收，不能依据“某能力已有一条规则”宣称所有机制覆盖。本文后续伤害公式和时间轴仍未实现。

### Fribbels 机制参考接入

参考 [Fribbels 白露配置](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/conditionals/character/1200/Bailu.ts) 的类型化治疗命中及独立星魂加成思路；不复制其两档满级倍率作为账号等级表，不将开关默认值视为实际已触发状态。实际数值继续引用 Station 常量/准确等级表。白露战技补充三次独立治疗和实际随机目标；四魂加成按每次受治疗者记录，不能直接照搬优化器的全队预设层数。

新增白露 28 条机制规则和 24 个条目、27 个条款的人工审核清单。贡献保留解析参数、参考提交与 `settlement` 元数据，区分基础伤害/治疗定义、读取实体、属性阶段及命中序号。期限支持 `duration.valueExpression` 引用来源参数，并校验正整数；减伤组合使用明确的补数乘算操作 `multiplicative_complement`。现有站街装备读取器保持不变，白露的战斗贡献不会混入站街属性。

人工规则编译与来源同步独立，使用 `build:catalogue-rules`，保护其他作者记录并将规则与覆盖报告同批发布。来源变化、无效引用、非法单位、循环依赖或未管理 ID 冲突时拒绝发布。全量审核仍不完整，必须通过 `--allow-pending` 明确发布阶段性覆盖；此参数不能将全量审核门禁改为成功。事件候选不自动修改资源、回合或递归触发后续事件。

## 1. 背景与结论

当前项目中的 Stat Score、遗器潜力和 Estimated TBP 是遗器质量与刷取成本的启发式指标，不是战斗伤害。后续增加伤害计算时，必须建立独立的战斗计算领域，不能把词条权重直接当作伤害权重。

Fribbels 将计算拆为三层：

1. 通用伤害引擎负责基础伤害、增伤、暴击、防御、抗性、易伤等乘区。
2. 命中定义负责声明一次伤害属于直伤、DoT、击破、超击破等类型，并提供 ATK／HP／DEF 倍率。
3. 角色、光锥、遗器和队友条件负责注入倍率、属性与动态 Buff。

本项目后续实现应保持相同的职责分离，但数据结构和代码必须适配现有 Vue 3 + Tauri 2 架构。

## 2. 目标与非目标

### 2.1 目标

- 计算一次命中、一个技能和一组自定义技能序列的期望伤害。
- 支持 ATK、HP、DEF 及混合倍率技能。
- 支持直伤、附加伤害、DoT、击破和超击破。
- 支持角色、光锥、遗器、队友、敌人参数及条件开关。
- 输出总伤害和各乘区明细，使结果可以解释和回归测试。
- 使用稳定 ID 区分角色变体，避免同名或多命途角色串用配置。

### 2.2 首期非目标

- 不模拟完整战斗时间轴、行动提前、拉条、能量循环或敌方行动。
- 不自动推断最佳配队和技能循环。
- 不承诺与游戏客户端每一位显示值完全一致；取整时机需要通过实测逐步校准。
- 不用伤害结果替代现有 Stat Score、Estimated TBP 或培养方案权重。
- 不在首期支持依赖复杂战斗历史的机制；未建模条件必须明确显示为未启用。

## 3. 术语、单位与计算约定

### 3.1 数值单位

计算内核统一使用小数：

| UI 显示       | 内核数值 |
| ------------- | -------: |
| 50% 暴击率    |   `0.50` |
| 120% 暴击伤害 |   `1.20` |
| 20% 属性抗性  |   `0.20` |
| 15% 易伤      |   `0.15` |

UI 层负责百分数与小数的转换，领域计算层不接受带 `%` 的字符串。

### 3.2 结果口径

- **非暴击伤害**：暴击倍率固定为 `1`。
- **暴击伤害**：暴击倍率固定为 `1 + CRIT DMG`。
- **期望伤害**：使用暴击概率加权，是优化和装备比较的默认口径。
- **技能总伤害**：技能内所有命中的结果之和。
- **序列总伤害（Combo DMG）**：所选技能序列中所有计入统计的命中之和。

必须在输出中显示当前口径，不允许把期望伤害标成“暴击伤害”。

### 3.3 取整约定

首期所有中间值使用 JavaScript `number` 保留精度，只在 UI 展示层取整。若后续实测证明游戏在特定阶段取整，应将规则记录为独立、可测试的舍入策略，不能散落在角色配置中。

### 3.4 Combat Score 边界

首期**不提供 Combat Score**，只提供命中伤害、技能总伤害和 Combo DMG。本文中的“战斗计算领域”不等于已经定义了 Combat Score。

若以后增加 Combat Score，必须另写设计说明，定义基准构筑、归一化区间、技能序列、队伍条件和版本。它不得复用 Stat Score 的词条权重，也不得覆盖或改名现有 Stat Score。没有完整时间轴之前，Combo DMG 也不能被称为 DPS。

### 3.5 输入规范化原则

输入层与公式层的职责分开：

- 输入层拒绝 `NaN`、`Infinity`、缺失必填字段和百分数字符串。
- 明确属于概率或系统硬上限的字段由公式层 `clamp`，例如暴击率、有效抗性和有效 DoT 概率。
- 可被游戏机制降低为负值的字段不能被输入层擅自归零；是否允许负值由字段契约规定。
- UI 可给出常用范围警告，但不能在用户不知情时修改输入。

首期字段约束：

| 字段                                           | 接受范围                    | 公式处理                                          |
| ---------------------------------------------- | --------------------------- | ------------------------------------------------- |
| `critRate`、`critRateBoost`                    | 有限数值                    | 合计后 clamp 到 `[0, 1]`                          |
| `critDamage`、`critDamageBoost`                | 有限数值，合计不得小于 `-1` | 不额外截断                                        |
| `defensePenetration`                           | 有限数值                    | 有效值上限为 `1`；允许负值表达增防                |
| `enemyResistance - resistancePenetration`      | 有限数值                    | clamp 到 `[-1, 0.9]`                              |
| `vulnerability`                                | 有限数值                    | 参考实现 clamp 到 `[0, 2.5]`，负值按 `0` 参与公式 |
| `effectHitRate`、`effectResistancePenetration` | 有限数值                    | 只对最终生效概率 clamp                            |
| `breakEffect`                                  | 必须大于等于 `-1`           | `1 + breakEffect`                                 |
| `breakEfficiencyBoost`                         | 必须大于等于 `-1`           | `1 + breakEfficiencyBoost`                        |
| 各种倍率与削韧                                 | 有限且大于等于 `0`          | 不静默截断；非法则报错                            |
| DoT `stacks`                                   | 大于等于 `1` 的整数         | 非法则报错                                        |
| Buff `stacks`、`maxStacks`                     | 大于等于 `0` 的整数         | 归并后限制有效层数                                |

## 4. 通用直伤公式

Fribbels 的直伤入口见 [`CritDamageFunction`](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/optimization/engine/damage/damageCalculator.ts#L103-L123)，基础倍率计算见 [`calculateInitialDamage`](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/optimization/engine/damage/damageCalculator.ts#L1019-L1053)。

```text
基础伤害 =
  ATK × ATK倍率
+ HP  × HP倍率
+ DEF × DEF倍率
+ 其他明确声明的基础伤害
```

```text
最终期望伤害 =
  基础伤害
× 韧性状态倍率
× 防御倍率
× 抗性倍率
× 易伤倍率
× 最终伤害倍率
× 增伤倍率
× 期望暴击倍率
× 真伤附加倍率
× 命中自身的其他独立倍率
```

注意：公式中的“真伤附加倍率”沿用参考实现 `TRUE_DMG_MODIFIER` 的命名，本质是对该次伤害的附加乘数，不表示这次伤害绕过防御或抗性。

### 4.1 基础伤害

```text
BaseDamage = ATK × atkScaling
           + HP  × hpScaling
           + DEF × defScaling
```

部分技能可声明属性转换后的攻击倍率：

```text
atkScaling' = atkScaling + beScaling × EffectiveBreakEffect
atkScaling' = atkScaling + elationAtkScaling × Elation

EffectiveBreakEffect =
  beCap 存在时：min(BreakEffect, beCap)
  beCap 缺失时：BreakEffect
```

只有角色配置明确声明时才应用这些转换，不能根据角色流派自动猜测。

### 4.2 韧性状态倍率

```text
BrokenMultiplier = 1.0  // 敌人处于弱点击破状态
BrokenMultiplier = 0.9  // 敌人未处于弱点击破状态
```

这里描述的是敌人当前是否已被击破，不是敌人是否具有对应属性弱点。

### 4.3 防御倍率

参考实现将攻击方等级固定为 80：

```text
AttackerLevelConstant = 80 + 20 = 100

DefenseMultiplier =
  100 /
  ((EnemyLevel + 20) × max(0, 1 - DefensePenetration) + 100)
```

`DefensePenetration` 表示本次命中生效的减防与无视防御合计。`max(0, ...)` 使超过 100% 的部分不再继续提高该乘区。实现依据见 [`calculateDefMulti`](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/optimization/engine/damage/damageCalculator.ts#L1055-L1057)。

为了未来支持等级上限变化，本项目接口仍应显式保留 `attackerLevel`，默认值为 `80`：

```text
LevelConstant = AttackerLevel + 20

DefenseMultiplier =
  LevelConstant /
  ((EnemyLevel + 20) × max(0, 1 - DefensePenetration) + LevelConstant)
```

### 4.4 抗性倍率

```text
EffectiveResistance =
  clamp(EnemyResistance - ResistancePenetration, -1.00, 0.90)

ResistanceMultiplier = 1 - EffectiveResistance
```

对应边界：

- 有效抗性 `90%` 时，倍率为 `0.10`。
- 有效抗性 `0%` 时，倍率为 `1.00`。
- 有效抗性 `-100%` 时，倍率为 `2.00`。

### 4.5 易伤、增伤和最终伤害倍率

```text
VulnerabilityMultiplier = 1 + clamp(Vulnerability, 0, 2.50)

DamageBoostMultiplier =
  1
  + GenericDamageBoost
  + MatchingElementDamageBoost
  + HitSpecificDamageBoost

FinalDamageMultiplier = 1 + FinalDamageBoost

TrueDamageMultiplier =
  1 + GlobalTrueDamageModifier + HitTrueDamageModifier
```

不同来源能否相加必须由 Buff 数据定义；计算引擎只消费已经归并好的统计值。

`HitSpecificDamageBoost` 是 Buff 系统按角色、技能类型、伤害类型、属性和标签过滤后，为当前命中解析出的增伤。普通直伤、附加伤害和 DoT 将它与通用及属性增伤放在同一加算乘区；击破和超击破不读取通用或属性增伤，只读取该命中明确适用的 `HitSpecificDamageBoost`。

### 4.6 暴击倍率

参考实现见 [`getCritMultiplier`](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/optimization/engine/damage/damageCalculator.ts#L1059-L1063)。

```text
EffectiveCritRate = clamp(CritRate + CritRateBoost, 0, 1)
EffectiveCritDamage = CritDamage + CritDamageBoost

ExpectedCritMultiplier =
  EffectiveCritRate × (1 + EffectiveCritDamage)
  + (1 - EffectiveCritRate)

等价于：
ExpectedCritMultiplier = 1 + EffectiveCritRate × EffectiveCritDamage
```

本项目应同时输出非暴击、暴击和期望三种结果，以方便核对游戏内数字。

## 5. 特殊伤害公式

### 5.1 附加伤害

附加伤害沿用通用直伤公式，但允许独立覆盖暴击率、暴击伤害和每跳系数。它必须作为独立命中建模，不能直接并入触发技能的倍率，否则会错误继承只作用于普攻、战技或追加攻击的 Buff。

### 5.2 DoT

DoT 见 [`DotDamageFunction`](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/optimization/engine/damage/damageCalculator.ts#L211-L312)。它使用基础伤害、防御、抗性、易伤、增伤等乘区，但默认不使用普通暴击乘区。

```text
EffectiveDotChance = min(
  1,
  DotBaseChance
  × (1 + EffectHitRate)
  × (1 - EnemyEffectResistance + EffectResistancePenetration)
)
```

本项目使用更安全的闭区间写法：

```text
RawDotChance =
  DotBaseChance
  × (1 + EffectHitRate)
  × (1 - EnemyEffectResistance + EffectResistancePenetration)

EffectiveDotChance = clamp(RawDotChance, 0, 1)
```

上游当前只做 `min(1, ...)`；本项目增加下界是输入防御，避免异常数据产生负概率。

一次成功生效的单跳伤害：

```text
LandedSingleTickDamage =
  BaseDamage
  × 韧性状态倍率
  × 防御倍率
  × 抗性倍率
  × 易伤倍率
  × 最终伤害倍率
  × 增伤倍率
  × 真伤附加倍率
  × tickCoefficient
```

`application.mode = "all-or-nothing"` 表示整段 DoT 都依赖本次命中，适用于普通新施加 DoT：

```text
ExpectedDotDamage =
  LandedSingleTickDamage × EffectiveDotChance
```

`application.mode = "existing-base-plus-conditional-extra"` 表示基础层已经存在，仅额外层依赖本次命中，适用于类似已有基础层、继续叠层的期望模型。字段约束：

- `stacks` 是最终总层数，必须为大于等于 `1` 的整数。
- `extraStackDamageRatio` 必须大于等于 `0`，表示**每个额外层伤害 ÷ 基础层伤害**。
- 角色配置提供的 `BaseDamage` 必须已经包含所有配置层数的完整倍率。

该模式使用：

```text
EhrMultiplier =
  (1 + extraStackDamageRatio × EffectiveDotChance × (stacks - 1))
  / (1 + extraStackDamageRatio × (stacks - 1))

ExpectedDotDamage =
  LandedSingleTickDamage
  × EhrMultiplier
```

当 `stacks = 1` 时没有“额外层”，该模式的 `EhrMultiplier = 1` 是有意行为；若整个单层也依赖命中，必须选择 `all-or-nothing`。聚合层不能再额外乘一次 `stacks`。结果页必须同时显示“成功生效后的单跳伤害”和“考虑命中概率的期望伤害”，避免用户混淆。

### 5.3 击破伤害

实现依据见 [`BreakDamageFunction`](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/optimization/engine/damage/damageCalculator.ts#L320-L393)。

```text
BreakBaseDamage =
  3767.5533
  × ElementBreakScaling
  × (0.5 + EnemyMaxToughness / 120)
  × SpecialScaling

BreakDamageBoostMultiplier =
  1 + HitSpecificDamageBoost
```

```text
BreakDamage =
  BreakBaseDamage
  × (1 + BreakEffect)
  × 韧性状态倍率
  × 防御倍率
  × 抗性倍率
  × 易伤倍率
  × 最终伤害倍率
  × BreakDamageBoostMultiplier
  × 真伤附加倍率
```

80 级角色的属性击破系数来自 [`calculateContext.ts`](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/optimization/context/calculateContext.ts#L56-L64)：

| 属性 | `ElementBreakScaling` |
| ---- | --------------------: |
| 物理 |                   2.0 |
| 火   |                   2.0 |
| 冰   |                   1.0 |
| 雷   |                   1.0 |
| 风   |                   1.5 |
| 量子 |                   0.5 |
| 虚数 |                   0.5 |

`3767.5533` 是参考实现采用的 80 级击破基础常量。若支持其他角色等级，应改为等级表查询，不能按比例外推。

击破字段约定：

- `SpecialScaling` 默认值为 `1`，只有角色或机制配置明确声明时才改变。
- `ElementBreakScaling` 取实际触发本次弱点击破的伤害属性，而不是角色头像的默认属性。
- `EnemyMaxToughness`、`ToughnessDamage` 和 `FixedToughnessDamage` 统一使用当前游戏显示削韧单位，例如标准普攻记为 `10`；领域层不再做隐藏的 3 倍或 30 倍换算。
- 弱点击破伤害按伤害结算时的状态计算，首期默认 `weaknessBrokenAtResolution = true`，即韧性状态倍率为 `1.0`。若对照上游兼容数据需要使用其他状态，fixture 必须显式传值并说明原因。

### 5.4 超击破伤害

实现依据见 [`SuperBreakDamageFunction`](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/optimization/engine/damage/damageCalculator.ts#L400-L488)。

```text
BreakEfficiencyMultiplier = 1 + BreakEfficiencyBoost

EffectiveToughnessDamage =
  BreakEfficiencyMultiplier × ToughnessDamage
  + FixedToughnessDamage

SuperBreakBaseDamage =
  (3767.5533 / 10)
  × EffectiveToughnessDamage

EffectiveSuperBreakModifier =
  CombatantSuperBreakModifier
  + HitExtraSuperBreakModifier

SuperBreakDamageBoostMultiplier =
  1 + HitSpecificDamageBoost
```

```text
SuperBreakDamage =
  SuperBreakBaseDamage
  × (1 + BreakEffect)
  × EffectiveSuperBreakModifier
  × 韧性状态倍率
  × 防御倍率
  × 抗性倍率
  × 易伤倍率
  × 最终伤害倍率
  × SuperBreakDamageBoostMultiplier
  × 真伤附加倍率
```

当 `EffectiveSuperBreakModifier = 0` 时，超击破伤害必须为 `0`。`extraSuperBreakModifier` 与角色面板或 Buff 归并后的 `superBreakModifier` 使用加法合并，不再作为另一个独立乘区。

超击破还有硬前置条件：敌人在该次伤害结算时必须已处于弱点击破状态。`weaknessBrokenAtResolution = false` 时不计算 `0.9` 倍超击破，而是返回 `0` 并在 breakdown 中记录 `inactiveReason: "enemy-not-broken"`。

### 5.5 欢愉伤害与其他扩展类型

参考项目还实现了治疗、护盾、基于治疗量的伤害、欢愉伤害和 Buff 数值转换，类型注册表见 [`DamageFunctionRegistry`](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/optimization/engine/damage/damageCalculator.ts#L986-L1001)。这些类型不进入首期，但领域模型应允许以后新增计算策略，不要通过一个不断增长的条件分支实现所有类型。

## 6. 角色技能与条件配置

### 6.1 角色变体主键

角色配置必须使用稳定 ID，显示名只能用于 UI：

```ts
type CharacterVariantKey = `hsr/${string}/${string}/${string}`;

interface CharacterVariantIdentity {
  variantKey: CharacterVariantKey;
  gameCharacterId: string;
  displayName: string;
  path: string;
  element: Element;
  form: string;
}
```

`variantKey` 是全局唯一、可持久化的规范键，格式为：

```text
hsr/<gameCharacterId>/<path>/<form>
```

例如可表达为 `hsr/1001/preservation/base`、`hsr/1224/hunt/base`。实际 ID 以项目角色数据为准，示例不能直接成为生产数据。

必须满足：

- 开拓者的毁灭、存护、同谐、记忆、欢愉等命途使用不同 `variantKey`。
- 三月七的存护与巡猎使用不同 `variantKey`。
- 装备、属性快照、技能倍率、星魂、行迹、数据查找和缓存都使用完整 `variantKey`，不能只绑定中文名、基础角色名或局部 `form`。
- 性别或形态会改变技能数据时，必须进入 `gameCharacterId` 或 `form`，并自然成为 `variantKey` 的一部分。
- 不允许在不同模块各自拼缓存键；统一由 `toCharacterVariantKey(identity)` 生成并校验。

参考项目同样使用独立角色文件，例如[存护三月七](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/conditionals/character/1000/March7th.ts#L69-L151)与[存护开拓者](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/conditionals/character/8000/TrailblazerPreservation.ts#L58-L192)。

### 6.2 命中定义

技能不是一个单独数字，而是一组命中。命中契约使用可辨识联合，避免某种伤害读取不到自己所需的字段：

```ts
type DamageKind = "direct" | "additional" | "dot" | "break" | "superBreak";

type AbilityKind = "basic" | "skill" | "ult" | "fua" | "talent" | "other";

interface ScalingDefinition {
  atk: number;
  hp: number;
  def: number;
}

interface BaseHitDefinition {
  id: string;
  abilityKind: AbilityKind;
  element: Element;
  repeat: number; // 默认 1，仅表示完全相同的重复命中
  recorded: boolean; // 默认 true；false 时可供后续命中引用但不计入总伤害
  trueDamageModifier: number; // 默认 0
  tags: string[];
}

interface DirectHitDefinition extends BaseHitDefinition {
  damageKind: "direct";
  scaling: ScalingDefinition;
  beToAtkScaling?: { coefficient: number; cap?: number };
  elationToAtkScaling?: number;
}

interface AdditionalHitDefinition extends BaseHitDefinition {
  damageKind: "additional";
  scaling: ScalingDefinition;
  critRateOverride?: number;
  critDamageOverride?: number;
  coefficient: number; // 默认 1
}

type DotApplication =
  | { mode: "all-or-nothing" }
  | {
      mode: "existing-base-plus-conditional-extra";
      extraStackDamageRatio: number;
      stacks: number;
    };

interface DotHitDefinition extends BaseHitDefinition {
  damageKind: "dot";
  scaling: ScalingDefinition;
  baseChance: number;
  application: DotApplication;
  tickCoefficient: number; // 默认 1
}

interface BreakHitDefinition extends BaseHitDefinition {
  damageKind: "break";
  specialScaling: number; // 默认 1
}

interface SuperBreakHitDefinition extends BaseHitDefinition {
  damageKind: "superBreak";
  toughnessDamage: number;
  fixedToughnessDamage: number; // 默认 0
  extraSuperBreakModifier: number; // 默认 0
}

type HitDefinition =
  | DirectHitDefinition
  | AdditionalHitDefinition
  | DotHitDefinition
  | BreakHitDefinition
  | SuperBreakHitDefinition;

interface ActionDefinition {
  id: string;
  abilityKind: AbilityKind;
  hits: HitDefinition[];
}
```

所有 `scaling` 都表示**一次命中**的倍率。只有多次命中在倍率、标签和 Buff 适用结果上完全相同时，才允许用 `repeat > 1`；否则必须拆成多个命中定义。

聚合规则：

```text
HitTotal = DamageStrategy(hit) × repeat

ActionTotal =
  sum(HitTotal where hit.recorded = true)

ComboDamage =
  sum(ActionTotal for action in requested actions)
```

`coefficient`／`tickCoefficient` 在对应策略内部只乘一次，聚合层不得再次使用。`recorded` 缺省归一化为 `true`。同一技能的不同命中可能吃到不同 Buff、削韧值或倍率，因此不能把技能预先压成一个总倍率。

### 6.3 条件和 Buff

条件系统至少要表达：

- 星魂与光锥叠影等级；
- 技能形态、强化状态、目标数量与命中次数；
- Buff／Debuff 是否生效及层数；
- Buff 的目标范围、伤害类型范围和属性范围；
- Buff 是加算、乘算、覆盖还是取上限；
- Buff 的来源 ID，供结果解释和排查重复叠加。

首期不支持的动态条件必须由用户显式输入，禁止静默采用看似合理的默认值。

建议的最小 Buff 契约：

```ts
type ModifierOperation = "add" | "multiply" | "max" | "override";

interface BuffScope {
  targetVariantKeys?: CharacterVariantKey[];
  abilityKinds?: AbilityKind[];
  damageKinds?: DamageKind[];
  elements?: Element[];
  requiredTags?: string[];
}

interface BuffDefinition {
  id: string;
  sourceId: string;
  stackingKey: string;
  stat: ScalarCombatStatKey;
  operation: ModifierOperation;
  valuePerStack: number;
  stacks: number;
  maxStacks: number;
  priority: number;
  scope: BuffScope;
}

interface ResolvedBuffContribution {
  sourceIds: string[];
  stackingKey: string;
  stat: ScalarCombatStatKey;
  operation: ModifierOperation;
  resolvedValue: number;
  priority: number;
}
```

归并必须确定且可解释：

1. 先按 `scope` 过滤本次命中不适用的 Buff。数组范围使用“包含即匹配”；多个范围字段之间是 AND；`requiredTags` 要求全部存在；字段缺省表示不限制。
2. 同一 `stackingKey` 的定义必须具有相同 `stat`、`operation`、`valuePerStack`、`maxStacks` 和 `priority`，否则视为数据错误。
3. 同一 `stackingKey` 的 `stacks` 相加后限制到 `[0, maxStacks]`，再计算 `resolvedValue = valuePerStack × effectiveStacks`。不允许仅凭显示名去重。
4. 同一统计项按 `add → multiply → max → override` 执行，数学语义分别为：

```text
add:      current = current + resolvedValue
multiply: current = current × (1 + resolvedValue)
max:      current = max(current, resolvedValue)
override: current = resolvedValue
```

5. 多个 `override` 取 `priority` 最大者；同优先级冲突视为配置错误，不按数组顺序碰运气。
6. 系统硬上限在所有 Buff 归并后应用。
7. breakdown 保留每个 `sourceId` 的输入值、有效层数、实际贡献和未生效原因。

每个 `CombatStatKey` 必须在注册表中声明允许的操作符；例如普通增伤通常允许 `add`，不能因为通用契约存在 `override` 就随意覆盖。

## 7. 建议的数据契约

以下接口是设计草案，落地前可根据现有 `types.ts` 调整名称，但语义不能丢失。

```ts
type Element = "physical" | "fire" | "ice" | "lightning" | "wind" | "quantum" | "imaginary";

interface CombatantStats {
  level: number;
  hp: number;
  atk: number;
  def: number;
  critRate: number;
  critRateBoost: number;
  critDamage: number;
  critDamageBoost: number;
  breakEffect: number;
  effectHitRate: number;
  effectResistancePenetration: number;
  elation: number;
  genericDamageBoost: number;
  elementalDamageBoost: Partial<Record<Element, number>>;
  defensePenetration: number;
  resistancePenetration: number;
  vulnerability: number;
  finalDamageBoost: number;
  globalTrueDamageModifier: number;
  hitSpecificDamageBoost: number;
  breakEfficiencyBoost: number;
  superBreakModifier: number;
}

type ScalarCombatStatKey =
  Exclude<keyof CombatantStats, "elementalDamageBoost"> | `elementalDamageBoost.${Element}`;

interface EnemyConfig {
  level: number;
  resistance: Partial<Record<Element, number>>;
  effectResistance: number;
  maxToughness: number;
  weaknessBrokenAtResolution: boolean;
  elementalWeaknesses: Element[];
}

interface DamageRequest {
  characterVariantKey: CharacterVariantKey;
  stats: CombatantStats;
  enemy: EnemyConfig;
  actions: ActionDefinition[];
  activeConditionIds: string[];
  buffs: BuffDefinition[];
}

// ActionDefinition 不重复保存角色键：一个请求只属于一个角色变体。
// 从角色数据装配 action 时，adapter 必须校验数据文件的 variantKey
// 与 DamageRequest.characterVariantKey 相同。

interface CommonDamageBreakdown {
  baseDamage: number;
  brokenMultiplier: number;
  defenseMultiplier: number;
  resistanceMultiplier: number;
  vulnerabilityMultiplier: number;
  damageBoostMultiplier: number;
  finalDamageMultiplier: number;
  trueDamageMultiplier: number;
  expectedDamage: number;
  activeBuffSourceIds: string[];
  inactiveBuffs: Array<{ sourceId: string; reason: string }>;
}

interface DirectDamageBreakdown extends CommonDamageBreakdown {
  damageKind: "direct" | "additional";
  critMultiplier: number;
  nonCritDamage: number;
  critDamage: number;
}

interface DotDamageBreakdown extends CommonDamageBreakdown {
  damageKind: "dot";
  applicationMode: DotApplication["mode"];
  effectiveChance: number;
  landedSingleTickDamage: number;
  ehrMultiplier: number;
}

interface BreakDamageBreakdown extends CommonDamageBreakdown {
  damageKind: "break";
  breakBaseDamage: number;
  elementBreakScaling: number;
  specialScaling: number;
}

interface SuperBreakDamageBreakdown extends CommonDamageBreakdown {
  damageKind: "superBreak";
  effectiveToughnessDamage: number;
  superBreakBaseDamage: number;
  effectiveSuperBreakModifier: number;
  inactiveReason?: "enemy-not-broken" | "modifier-is-zero";
}

type DamageBreakdown =
  DirectDamageBreakdown | DotDamageBreakdown | BreakDamageBreakdown | SuperBreakDamageBreakdown;
```

输入解析必须校验有限数值、百分比范围和必填字段，计算内核不接收 `NaN`、`Infinity` 或 UI 文本。

## 8. 在本项目中的模块边界

遵循 `docs/架构设计.md` 的 `app → pages → features → shared` 依赖方向，建议新增独立领域：

```text
src/features/damage-calculator/
├── index.ts                # feature 对 page 暴露的唯一入口
├── components/             # 输入面板、乘区明细、结果视图
├── composables/            # 页面局部状态、请求取消、结果编排
├── domain/
│   ├── formulas.ts         # 无副作用通用公式
│   ├── damage-strategies.ts# 直伤、DoT、击破、超击破策略
│   ├── buffs.ts            # Buff 归并和适用范围
│   ├── rotation.ts         # 命中与技能序列聚合
│   └── contracts.ts        # feature 内部契约
└── data/                   # 仅服务本功能的角色技能配置

src/pages/
└── DamageCalculatorPage.vue # 组合伤害 feature 与角色/库存数据
```

架构约束：

- 纯公式优先放在 feature 的 `domain/`，由 Vitest 直接测试。
- 只有确认被多个领域稳定复用后，才把契约或纯函数提升到 `shared/`。
- `DamageCalculatorPage.vue` 负责组合库存角色、装备和计算器；伤害 feature 不得导入 inventory feature 内部文件。
- 若需要读取 SQLite 或调用 Rust，必须经 `src/shared/api/damage-calculator.ts`，Vue 组件不能直接调用 Tauri。
- 角色倍率数据与计算代码分离，数据更新不应要求修改通用公式。
- 不新增另一个集中式万能文件；公式、Buff、序列聚合和角色数据分别可测。

最小依赖和数据流：

```text
app/navigation.ts
  → DamageCalculatorPage.vue
      ├→ shared/api/inventory.ts（可选：读取角色与装备）
      ├→ shared/catalogue（只读角色/装备索引）
      └→ features/damage-calculator/index.ts
           → composable → domain formulas / strategies
```

集成清单：

- 在 `src/app/navigation.ts` 注册页面元数据，并由 `App.vue` 按现有页面装配方式加载。
- 计算器输入默认保留在页面或 composable；只有产品明确需要跨页面恢复时才进入 runtime store。
- 页面通过 `shared/api/inventory.ts` 或稳定的 shared 契约获取库存数据，再转换成 `CombatantStats`；damage feature 不导入 inventory feature。
- `src/features/damage-calculator/index.ts` 只导出稳定组件、composable 和领域请求契约，隐藏内部文件。
- 角色数据文件必须携带 `gameVersion`、`source`、`sourceRevision` 和 `updatedAt`，结果也回显所用版本。

### 8.1 前端还是 Rust

首期建议把纯计算放在 TypeScript：

- 公式计算无 I/O，便于即时预览和 Vitest 回归。
- 与当前遗器评分的纯前端计算方式一致。
- 首期计算规模远小于全遗器排列优化，不需要 Rust 或 WebGPU。

角色数据持久化、版本迁移或大规模装备搜索若以后成为性能瓶颈，再设计 Rust 用例和 command；不能提前把公式拆成前后端两份实现。

## 9. 推荐实施阶段

### 阶段 1：纯公式内核

- 定义 `Element`、`DamageKind`、`HitDefinition`、`CombatantStats`、`EnemyConfig`。
- 实现并测试基础伤害、防御、抗性、易伤、增伤和暴击乘区。
- 返回完整 `DamageBreakdown`，暂不制作复杂 UI。

### 阶段 2：手输直伤 MVP

- 支持 ATK／HP／DEF 混合倍率。
- 支持普攻、战技、终结技、追加攻击标签。
- 支持角色面板手输和敌人参数手输。
- 展示非暴击、暴击、期望伤害及乘区明细。
- 本阶段不读取角色、装备或库存，因此不宣称支持角色变体集成。

### 阶段 3：特殊伤害

- 增加附加伤害、DoT、击破和超击破策略。
- 增加效果命中、效果抵抗、削韧和击破效率输入。
- 对照公开计算器和游戏内样本建立回归数据。

### 阶段 4：角色集成 MVP

- 建立按 `characterVariantKey` 隔离的技能配置。
- 从库存只读组合角色、光锥和遗器面板。
- 增加队友 Buff、光锥、遗器套装和条件开关。
- 将每个结果追溯到倍率与 Buff 来源。

### 阶段 5：技能序列与装备优化

- 支持用户配置技能序列和命中次数。
- 计算 Combo DMG，但明确不等同于单位时间 DPS。
- 在公式稳定且有性能基准后，才评估全库存装备排列优化。

## 10. 测试基线

### 10.1 通用乘区样例

输入：

```text
ATK = 3000
ATK倍率 = 2.0
通用增伤 = 50%
属性增伤 = 20%
暴击率 = 70%
暴击伤害 = 140%
敌人等级 = 95
减防/无视防御 = 20%
敌人抗性 = 20%
抗性穿透 = 10%
易伤 = 15%
最终伤害提高 = 10%
敌人未击破
```

中间值：

```text
基础伤害 = 3000 × 2 = 6000
增伤倍率 = 1 + 0.5 + 0.2 = 1.7
期望暴击倍率 = 1 + 0.7 × 1.4 = 1.98
防御倍率 = 100 / ((95 + 20) × 0.8 + 100) = 100 / 192
抗性倍率 = 1 - (0.2 - 0.1) = 0.9
易伤倍率 = 1.15
最终伤害倍率 = 1.1
韧性状态倍率 = 0.9
```

期望结果：

```text
6000 × 1.7 × 1.98 × (100 / 192) × 0.9 × 1.15 × 1.1 × 0.9
= 10778.0371875
```

展示层可显示为 `10,778`，测试应断言未取整数值。公式单测使用绝对误差 `1e-6`；跨实现或外部 fixture 比较使用相对误差 `1e-6`，两者满足其一即可。

### 10.2 击破与超击破数值样例

共同输入：

```text
角色等级 = 80
敌人等级 = 95
敌人抗性 = 20%
减防/无视防御 = 0
抗性穿透 = 0
击破特攻 = 150%
敌人在伤害结算时已被击破
其他增伤、易伤和独立倍率 = 0
防御倍率 = 100 / 215
抗性倍率 = 0.8
```

物理击破，敌人最大韧性为 `360`：

```text
BreakBaseDamage = 3767.5533 × 2.0 × (0.5 + 360 / 120)
BreakDamage = BreakBaseDamage × 2.5 × (100 / 215) × 0.8
BreakDamage = 24532.90520930233
```

超击破，技能削韧 `20`、固定削韧 `0`、击破效率提高 `50%`、超击破倍率 `1.0`：

```text
EffectiveToughnessDamage = 1.5 × 20 + 0 = 30
SuperBreakBaseDamage = (3767.5533 / 10) × 30
SuperBreakDamage = SuperBreakBaseDamage × 2.5 × 1.0 × (100 / 215) × 0.8
SuperBreakDamage = 10514.10223255814
```

这两个样例只校验本文定义的数学口径；在获得固定游戏版本的实测样本后，还需增加独立的游戏对照 fixture。

### 10.3 DoT 数值样例

除命中概率外的乘区均设为 `1`。

普通整段依赖命中的 DoT：

```text
application.mode = all-or-nothing
LandedSingleTickDamage = 1000
DotBaseChance = 0.5
EffectHitRate = 0.2
EnemyEffectResistance = 0.4
EffectResistancePenetration = 0

EffectiveDotChance = 0.5 × 1.2 × 0.6 = 0.36
ExpectedDotDamage = 1000 × 0.36 = 360
```

已有基础层、额外层依赖命中的 DoT：

```text
application.mode = existing-base-plus-conditional-extra
基础层伤害 = 1000
extraStackDamageRatio = 0.1
stacks = 4
LandedSingleTickDamage = 1000 × (1 + 0.1 × 3) = 1300
EffectiveDotChance = 0.5

EhrMultiplier = (1 + 0.1 × 0.5 × 3) / (1 + 0.1 × 3)
              = 1.15 / 1.3
ExpectedDotDamage = 1300 × (1.15 / 1.3) = 1150
```

这两个 fixture 分别证明整段命中概率和仅额外层命中概率不会混用。

### 10.4 必测边界

- 暴击率为 `0`、`1` 和超过 `1`。
- 减防为 `0`、`1` 和超过 `1`。
- 有效抗性分别落在正数、`0`、负数和上下限之外。
- 易伤为负数、`0`、正常值和超过 `2.5`。
- ATK、HP、DEF 单倍率与混合倍率。
- 敌人已击破和未击破。
- DoT 命中率不足与达到 100%。
- DoT 多层分摊和每跳系数。
- DoT `stacks = 0`、非整数层数和负 `extraStackDamageRatio` 返回校验错误。
- 七种属性击破系数。
- 超击破倍率为 `0`、削韧为 `0`、带固定削韧。
- 敌人未击破时超击破返回 `0` 和明确的 `inactiveReason`。
- 同名不同变体角色不会共用技能、装备或缓存。
- 多命中技能只对符合标签的命中应用 Buff。
- Buff 的 `add`、`multiply`、`max`、`override` 各有数值 fixture，并覆盖同优先级覆盖冲突。
- 输入含 `NaN`、`Infinity`、缺失字段或错误百分比格式时返回可读校验错误。

### 10.5 对照测试

每个已支持角色至少保留以下 fixture：

1. 无装备、无 Buff 的基础技能结果。
2. 一套固定面板与固定敌人的非暴击、暴击、期望结果。
3. 一个星魂或行迹条件开关前后的差值。
4. 一个队友或装备 Buff 的适用与不适用命中。
5. 若有变体，同名角色的交叉隔离测试。

fixture 至少保存：`gameVersion`、角色规范键、技能等级、星魂、光锥与叠影、完整面板、敌人参数、启用条件、预期结果、来源和采集日期。禁止使用会随 `main` 漂移的外部结果作为测试时实时依赖。

## 11. 风险与待确认项

| 项目               | 当前处理                            | 后续确认方式                       |
| ------------------ | ----------------------------------- | ---------------------------------- |
| 游戏内取整时机     | 中间值不取整                        | 用录屏或固定面板逐乘区校准         |
| 角色技能倍率来源   | 版本化静态数据                      | 保存来源、游戏版本和更新时间       |
| Buff 同类叠加规则  | 数据显式声明操作符                  | 为相加、乘算、取大、覆盖分别写测试 |
| 多目标／扩散／弹射 | 每个目标或命中单独定义              | 对照技能说明和实测                 |
| DoT 口径           | 同时展示挂上后与概率期望            | UI 明确标签                        |
| Combo DMG 与 DPS   | Combo 仅为序列总伤害                | 未建模行动时间前不显示 DPS         |
| 参考实现更新       | 锁定提交，不自动追随 `main`         | 升级时做公式与角色数据差异审计     |
| 许可证与归属       | 公式可参考；复制实现需审查 MIT 要求 | 保留上游链接、许可证和必要声明     |

## 12. 实现验收条件

### 12.1 手输直伤 MVP

- 通用公式全部为纯函数并有边界测试。
- UI 能显示输入、三种伤害口径和乘区明细。
- UI 明确标为“手动直伤计算”，不暗示已经读取角色技能、装备或队伍。
- 页面不显示 Combat Score 或 DPS，只显示 Damage 与所选技能的总伤害。
- 不支持的伤害类型禁用或明确标记，不静默按直伤计算。
- 现有 relic-score 单测保持通过，并增加一个 UI 文案测试确认 Stat Score 与伤害计算的区别。
- 公式测试满足第 10.1 节误差要求。
- `npm run check` 通过；涉及 Rust 时 `npm run check:rust` 也通过。

### 12.2 特殊伤害 MVP

- DoT、击破和超击破使用独立策略与可辨识 breakdown。
- 第 10.2、10.3 节全部数值 fixture 满足既定误差要求。
- DoT 两种 `application.mode` 均有正常值和非法输入测试；`stacks` 只接受大于等于 `1` 的整数。
- 七种击破属性系数、`specialScaling` 默认值和削韧单位均有测试。
- 超击破只在敌人已击破且有效超击破倍率非零时产生伤害，其他情况返回可解释的 `inactiveReason`。
- UI 明确显示 DoT 生效后伤害、有效概率和概率期望，不显示不适用的暴击字段。

### 12.3 角色集成 MVP

- 满足手输直伤 MVP 的全部条件。
- 角色变体使用规范 `variantKey`，三月七和开拓者不同命途的交叉隔离测试通过。
- 角色、装备、Buff、敌人和结果携带可展示的游戏版本与来源修订。
- 每个已支持角色具有第 10.5 节规定的版本化 fixture。
- breakdown 能列出实际生效和未生效的 Buff 来源及原因。
- 支持机制清单与角色数据同版本发布；缺少配置的机制在 UI 显示“当前版本未建模”。
