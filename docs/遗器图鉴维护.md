# 公共图鉴数据维护

统一同步现使用隔离 JSON 候选目录，所有任务成功后同批发布；条款编译为最后一个任务，可单独执行 `npm run sync:catalog -- mechanisms`。图片不计入 JSON 事务。编译器当前的覆盖边界及具体缺项见 [近似机制执行维护](./近似机制执行维护.md)。

## 目的与边界

`src/data/relic-sets.json`、`src/data/characters.json` 和 `src/data/light-cones.json` 是随桌面客户端打包的公共图鉴：`relic-sets.json` 保存套装 ID、名称、类别、2/4 件效果、套装图标和各部位图标；`characters.json` 保存角色名称、属性、命途、头像和 80 级满突破的基础面板；`light-cones.json` 保存光锥 ID、名称、稀有度、命途、图标、80 级满突破的基础面板，以及技能名称与叠影 1–5 的效果文案。套装的 `pieces` 会明确标记部位：`Head`、`Hands`、`Body`、`Feet` 或 `PlanarSphere`、`LinkRope`。它们不依赖游戏登录或用户背包，也不会写进 `inventory.sqlite3`。

装备路径的站街计算读取 `standing-rule-definitions.json` 中按来源 ID 人工审阅的属性与转换规则，不再推断中文文案。旧字符串解析器仅保留兼容调用和回归测试。站街审核不等于战斗机制完整审核；缺少可信属性（例如能量上限）时必须明确展示缺失，不能默认零。

SQLite 只保存用户的遗器、角色、光锥和毕业方案；公共图鉴放入该数据库会让"清空背包"和"更新公共数据"互相干扰。

## 更新时机

游戏新增、调整遗器/饰品套装或光锥，或准备发布客户端时执行一次。日常启动客户端不访问数据源网站。

## 同步命令

要求 Node.js 22+ 和能访问数据源网站。

### 统一入口（推荐）

```bash
npm run sync:all                              # 一键同步全部
npm run sync:catalog                          # 默认也是全部
npm run sync:catalog -- relic                  # 遗器与角色基础图鉴
npm run sync:catalog -- light-cone             # 光锥
npm run sync:catalog -- mechanic               # 技能与机制来源
npm run sync:catalog -- relic light-cone        # 选择多个任务
npm run sync:catalog -- all --skip-images      # 全部同步，但不下载图片
npm run sync:catalog -- all --refresh-images   # 基础图鉴重新下载图片
npm run sync:catalog -- --list                 # 查看任务与参数
```

统一入口按遗器/角色 → 光锥 → 机制来源的顺序串行执行，使用当前 Node 可执行文件；任一任务失败立即停止。各任务仍独立发布，前面已经成功的任务不会因后续失败而整体回滚。图片参数只传给支持图片同步的任务。它不修改人工审核记录，也不把全量机制审核作为来源同步成功条件；审核仍单独执行 `validate:mechanic-catalog`。下方原有独立命令继续可用。

### 技能、行迹、星魂与召唤物

```bash
npm run sync:mechanic-catalog -- --dry-run
npm run sync:mechanic-catalog
npm run validate:mechanic-catalog -- --write-report
```

统一来源存入 `src/data/catalogue-mechanics.json`，变更清单在 `catalogue-mechanics-report.json`。同步从角色、光锥和遗器列表读取明确 ID 映射，角色不同命途独立记录；网站节点 ID 不是游戏技能 ID。技能名称、模板和分组只记录一次，所有来源参数保存为常量或准确等级表，包括未显示参数与来源提供的 11–15 级；不拟合等级公式。

来源适配在 `scripts/lib/catalogue-source.mjs`，审核规则与抓取结果必须分文件维护，来源同步不得覆盖人工审核。模板、参数、类型与分组进入内容指纹，图标及更新时间不进入机制指纹。来源变化后旧审核规则禁止求值。`--dry-run` 不发布；任一来源抓取/适配失败，不替换既有公共机制 JSON。

`catalogue-mechanics-fingerprints.json` 与来源数据在同一批生成，供站街读取器检查 `standing-rule-bindings.json` 的人工审阅指纹。后者仅在逐叠影描述核对通过后记录，来源同步不会更新它；参数、类型或分组变化会使相应站街来源失效。装备路径还会核对角色命途，命途不符的光锥技能不贡献属性；基础三围仍由现有面板计算汇总。整数与百分比指定小数位属于模板展示格式，原始参数不做舍入。

新机制同步和原有两个同步器均使用 `catalogue-publication.mjs`：先完整准备候选文件、暂存并验证，再替换；异常尝试恢复原文件。该保证针对同一次进程内 JSON 发布，不宣称多文件跨进程崩溃原子性；图片下载不在 JSON 回滚事务中。发布时不要并发运行多个同步器。

当前机制来源全量同步与战斗机制全量审核是两个独立门禁。`auditStatus: pending` 不能视为规则库验收完成；逐条审核需关联真实规则或说明文字的明确排除理由，不能以空效果或“其他效果”占位计入覆盖率。

`validate:mechanic-catalog` 使用客户端同一校验器，对 `catalogue-rules.json` 的规则和逐条审核清单检查来源指纹、引用及覆盖。缺少审核清单或全量覆盖不完整时返回非零退出码；`--write-report` 保存 `catalogue-audit-report.json`，不能把普通单元测试通过替代此全量审核门禁。

本次来源清单包含 97 个角色、169 个光锥、60 套遗器，含召唤物共 2967 个能力条目。`catalogue-rules.json` 包含远坂凛、知更鸟·晴歌与绯英的 103 条机制，以及白露新增的 28 条规则。白露 24 个能力条目的 27 个描述条款有明确审核清单；普通地图攻击的削韧条款仍未标注。其余来源完整条款审核尚未完成，全量审核门禁预期失败。此状态是阶段性实现，不是方案中“所有来源审核覆盖完成”的验收结果。

### 参考机制与人工规则编译

参考 [Fribbels 角色机制实现](https://github.com/fribbels/hsr-optimizer/tree/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/conditionals/character)，固定参考提交 `d28928b1f09d7613c37ca7ca373a468367060fc0`。不执行外部代码，也不从描述自动生成审核结论。新白露规则由 `scripts/lib/bailu-mechanic-rules.mjs` 人工维护：固定 Station 内容指纹、按明确节点 ID 绑定参数，并记录参考链接、版本及适配说明。

```bash
npm run build:catalogue-rules -- --dry-run        # 离线编译并校验，不写入
npm run build:catalogue-rules -- --allow-pending  # 明确发布本期部分覆盖
npm run build:catalogue-rules -- --check          # 检查打包规则与报告是否可重复生成
npm run validate:mechanic-catalog                # 独立全量审核门禁，当前预期非零
```

编译器保留其他人工规则与审核记录，只替换 `compiled.bailu` 清单中标明的生成记录；与未管理记录发生 ID 冲突时拒绝覆盖。来源指纹变化时停止发布，必须先重新人工审核，不会自动换成新指纹。规则和覆盖报告同批发布，发布期间不能并发运行同步或编译任务。`--check` 检查可重复生成，不代表全量审核通过；未指定 `--allow-pending` 的写入要求完整覆盖。原 `sync:all` 仍仅同步来源，不执行人工审核编译。

白露的战技三次治疗分别定义，使用 `target.bailuSkillHit0/1/2` 指定实际落点，可以命中同一友方目标。治疗基数为 `owner.maxHp × p1 + p2`；后续两次分别乘 `1-p3` 和 `(1-p3)²`，不按敌人数或友方人数平均分配。`owner.maxHp` 是白露当前有效的生命上限，不是剩余生命值。`settlement` 明确记录属性实体和阶段、命中时读取；输出仍是基础治疗量，未合并治疗加成、目标受治疗加成、生命上限截断及游戏取整。

二魂在终结技事件后产生独立治疗量加成；四魂在 `bailu.skill.healed` 事件后给实际受治疗者增加一层增伤，记录上限和期限，不无条件赋给全队。生息的施加、延长、次数消耗与致命保护分别返回类型化状态/资源定义。调用方提供生息标记、剩余回合、次数、实际事件目标及已汇总的 `bailu.invigorationChargeLimit`；缺失时返回未知。基础次数和行迹/六魂额外次数以 `capacity.bailu.*` 独立贡献记录。减伤使用 `multiplicative_complement` 元数据，含义是多个比例按 `1-∏(1-r)` 合成，不把减伤比例直接乘到伤害上。

`accountLevelDeltas` 记录白露三魂/五魂加级与上限，客户端通过 `bundledAccountLevelDeltas` 显式传入现有账号适配器。账号输入仍要求基础技能等级，不要将已加级的等级再次作为基础等级传入；来源、身份或解锁缺失时不加级。本期不更改直读协议或自动接入战斗模拟。

图鉴状态分为“数值已同步，计算规则未标注”“部分机制可计算”“机制已审核”。最后一项要求来源指纹一致且逐条审核清单通过完整校验；它仅表示描述条款已映射为求值定义，不代表伤害公式或自动触发链已经实现。

`standing-catalogue-rules.json` 是统一 AST 的迁移候选，包含 160 条规则、95 个明确空结果和 6 个数值曲线不匹配的拒绝项（21007、21026、23040、23049、23059、23063）。它尚未接入运行时，不能视为 canonical 迁移完成；实际装备站街路径当前使用全量审阅定义与受保护的来源绑定。旧光锥叠影文案、遗器字符串及兼容读取器仍保留，完整消费者迁移后才可移除重复文案。

### 遗器与角色

```bash
npm run sync:relic-catalog
```

脚本会从遗器页与角色页生成两个 JSON，并下载图片到 `public/relic-sets/`、`public/relic-pieces/`、`public/characters/` 和 `public/character-icons/`。

### 光锥

```bash
npm run sync:light-cone-catalog
```

脚本会从光锥页生成 `src/data/light-cones.json`，并下载图标到 `public/light-cones/`。

### 通用参数

如只需先核对文字结构，可执行：

```bash
npm run sync:relic-catalog -- --skip-images
npm run sync:light-cone-catalog -- --skip-images
```

默认会跳过本地已经存在的图片，仅更新 JSON 数据。只有确认要重新下载全部图片时，才使用：

```bash
npm run sync:relic-catalog -- --refresh-images
npm run sync:light-cone-catalog -- --refresh-images
```

两个脚本在解析到过少条目时都会失败且不会覆盖当前 JSON，防止站点结构变更导致空数据提交。

## 更新后的核对与提交

1. 检查 JSON 的 `source.syncedAt`、新增 ID/角色/光锥、名称、效果描述、光锥 `skill.effects`（叠影文案）、角色属性/命途和 `kind`（`cavern` 为隧洞遗器，`planar` 为位面饰品）。
2. 检查 `public/relic-sets/`、`public/relic-pieces/`、`public/characters/`、`public/light-cones/` 是否有对应图片，并启动客户端确认图鉴、毕业方案下拉项、角色头像与光锥技能展示。
3. 执行 `npm run build`。
4. 将 JSON、图片和本维护文档一起提交；不要提交用户的 SQLite 数据库。

## 数据源变更处理

遗器与角色的同步逻辑位于 `scripts/sync-relic-catalog.mjs`，它按详情链接 `/cn/relics/<套装 ID>` 解析卡片。光锥的同步逻辑位于 `scripts/sync-light-cone-catalog.mjs`，它解析页面嵌入的 `window.PAGE_CONFIG` JSON 对象。若页面 HTML 结构发生变化，脚本会保护旧数据并退出。此时应更新脚本中的解析规则，再重新同步。

该图鉴来源于第三方站点。发布前请持续核对该站点的使用条款和图片再分发许可；JSON 中保留数据源 URL 仅用于追溯，并不表示客户端运行时会联网。
