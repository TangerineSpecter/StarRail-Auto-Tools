# 角色评分缓存说明

> **用途**：说明「评级 / 潜力 / 综合完成」如何计算、何时写入本地库、配队列表如何读取。  
> **相关实现**：
>
> - 计算：`src/shared/utils/relic-score/`（与角色详情、Stat Score 同源）
> - 持久化：SQLite 表 `character_build_scores`，API 见 `src/shared/api/character-score.ts`
> - 配队展示：`src/features/team/`  
>   **说明**：本文描述的是**派生评分缓存**，不是游戏内官方面板，也不是伤害模拟。

---

## 1. 要解决什么问题

| 误区                                  | 实际                                            |
| ------------------------------------- | ----------------------------------------------- |
| 角色列表接口已经带了评级/潜力         | **没有**。列表只有档案摘要（等级、命途等）      |
| 详情页能看到分数 = 库里有一条评分记录 | 早期只是**打开详情时现场算**，并不落库          |
| 配队再展示分数就要「整表重算一遍」    | 有缓存后：**优先读库**；只有没算过/已失效才补算 |

**结论**：

- **持久化的原料**：装备遗器、培养方案（权重/主词条目标等）
- **派生量**：字母评级、平均潜力%、综合完成%
- 派生量算过之后写入 `character_build_scores`，供配队等场景复用

---

## 2. 分数是什么

三个指标与角色详情「词条质量」面板、毕业看板口径一致：

| 字段                     | 含义                     | 大致算法                                                                         |
| ------------------------ | ------------------------ | -------------------------------------------------------------------------------- |
| **评级** `letterGrade`   | 六件平均潜力对应的字母档 | `letterGradeFromPotential(平均潜力%)`                                            |
| **潜力** `potentialPct`  | 已装备遗器的平均潜力     | `averageCharacterPotential`                                                      |
| **完成** `completionPct` | 综合完成度 0～100        | `planQualityCompletion` 的 `combinedRatio × 100`（主词条正确率与质量达标的综合） |

### 2.1 权重从哪来

```text
有培养方案 → 用方案的 substatWeights / effectiveSubstats / mainStats / minPotentialPct
无培养方案 → resolvePlanWeights({}) → 默认按暴击输出（critDps）模板
```

与 `CharacterScorePanel` 在 `plan == null` 时的行为一致：**不是**历史脏数据，而是**默认权重**。

### 2.2 没穿遗器

无法打分：不写有效缓存（或删除已有缓存）。配队槽位显示「未装备遗器」。

## 3. 存储结构

### 3.1 表 `character_build_scores`

| 列               | 说明                          |
| ---------------- | ----------------------------- |
| `character_id`   | 主键，角色 ID                 |
| `letter_grade`   | 如 `A-`、`S`                  |
| `potential_pct`  | 平均潜力 %                    |
| `completion_pct` | 综合完成 %                    |
| `relic_count`    | 参与计分的遗器件数            |
| `has_plan`       | 是否用了已保存培养方案（0/1） |
| `computed_at`    | 计算时间（毫秒时间戳）        |

Schema 版本：`SCHEMA_VERSION = 12`（见 `src-tauri/src/inventory/models.rs`）。

### 3.2 前后端契约

```ts
interface CharacterBuildScore {
  characterId: number;
  letterGrade: string;
  potentialPct: number;
  completionPct: number;
  relicCount: number;
  hasPlan: boolean;
  computedAt: number;
}
```

Tauri commands：

| command                        | 作用                        |
| ------------------------------ | --------------------------- |
| `upsert_character_build_score` | 写入/更新一条缓存           |
| `list_character_build_scores`  | 按 characterId 列表批量读取 |
| `delete_character_build_score` | 删除单条缓存                |

配队列表 `list_teams` 的每个成员可带 `score`（有缓存时），避免配队页再单独拼表。

## 4. 何时计算、何时失效

### 4.1 写入（计算并 upsert）

| 入口               | 行为                                                         |
| ------------------ | ------------------------------------------------------------ |
| **打开角色详情**   | 详情评分面板根据当前装备 + 方案（或默认权重）计算后 `upsert` |
| **保存培养方案**   | 后端先**删掉**该角色旧缓存；前端再按新方案重算并 `upsert`    |
| **删除培养方案**   | 后端删缓存；前端用默认权重重算（有装备则再写）               |
| **配队列表缺缓存** | 仅对「库里还没有分」的成员：拉装备 + 方案 → 算 → `upsert`    |

算法始终在**前端**执行（与详情同源）；后端只负责存取结果。  
当前没有把完整 Stat Score 引擎搬到 Rust。

### 4.2 失效（删除缓存）

| 入口                                      | 行为                                                 |
| ----------------------------------------- | ---------------------------------------------------- |
| **保存/删除培养方案**                     | 该 `character_id` 的缓存删除（再由前端重算）         |
| **背包同步 / 快照导入**（含 WebDAV 恢复） | 装备可能大变 → **清空整张** `character_build_scores` |
| **本地清空 / 批量删除**（遗器、角色等）   | 同样 **清空整张** 评分缓存，避免 miss 补洞刷不掉旧分 |
| **无遗器时重算**                          | `delete` 该角色缓存                                  |

在途补算使用 **世代校验**（`inventoryRevision` + 请求 id）：若中途发生同步/清空，已发出的重算 **不会再 upsert**，避免把同步前的分写回库。

游戏账号切换本身不单独处理评分表；若走全量清库/同步，会随装备失效策略一起清掉。

### 4.3 流程示意

```text
【详情打开 / 方案保存】
  装备 + 权重 → 计算 → upsert character_build_scores

【配队打开】
  list_teams（members 可带 score）
       ↓
  合并 list_character_build_scores
       ↓
  仍缺的 characterId → 补算一次并 upsert
       ↓
  卡片展示：评级 / 潜力 / 完成
  （加载中：评分加载中…；真无装备：未装备遗器）

【游戏同步改装备】
  DELETE 全部 character_build_scores
  （下次详情或配队再填缓存）
```

## 5. 和「角色列表」的关系

角色列表（遗器/光锥/角色档案 Tab）**不会**返回评分，也**不需要**为了列表性能去 join 评分表。

评分缓存的消费者目前主要是：

1. **配队列表**（主场景）
2. 其它页面若需要，可走 `list_character_build_scores`

角色详情始终可以自己算一遍用于展示；顺带写缓存是为了别处复用。

## 6. 与 WebDAV 的关系

| 数据         | 是否进 WebDAV                   |
| ------------ | ------------------------------- |
| 培养方案     | 是（`build-plans-*.json`）      |
| 本地配队     | 是（`teams-*.json`，format v3） |
| **评分缓存** | **否**                          |

评分是本地派生缓存：下载/覆盖本地背包后缓存会被清空，之后在详情或配队使用时再填充。  
避免把「默认权重算出的过期分」当成同步真相。

详见 [WebDAV数据同步.md](./WebDAV数据同步.md)。

## 8. 已知局限

1. **无方案时的默认分是 critDps 向**，对辅助/生存角色可能偏「好看或难看」，仅作参考；要贴合定位请保存培养方案。
2. **同步后首次打开**配队/详情会重新算一遍，属预期。
3. **算法在前端**：多端若将来扩展，需保证各端版本算法一致，或再考虑 Rust 侧重算。
4. 本地批量删除/清空与同步一样会整表失效评分；失效后由详情打开或配队 miss 补洞再写入。

---

## 9. 一句话总结

> **装备和方案是真相；评分是算出来的缓存。**  
> 详情打开、方案变更时写入；配队优先读缓存，没有才补算；背包同步则整表作废。
