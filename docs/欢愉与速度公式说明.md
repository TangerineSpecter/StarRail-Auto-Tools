# 欢愉与速度公式说明

本文记录 Fribbels [HSR Optimizer](https://github.com/fribbels/hsr-optimizer) 中与**欢愉伤害、阿哈速度和角色速度**有关的计算口径，供本项目后续开发计算器、角色面板或构建分析功能时使用。

> **核对基线**：上游 `main` 分支提交 [`d28928b1f09d7613c37ca7ca373a468367060fc0`](https://github.com/fribbels/hsr-optimizer/commit/d28928b1f09d7613c37ca7ca373a468367060fc0)，核对日期 2026-09-11。  
> **使用边界**：上游包含测试服数据，常量和角色倍率可能随版本调整。实现时应把通用公式、版本常量和角色倍率分开维护，并在游戏版本更新后重新核对。

## 1. 结论

上游存在三类不同的计算，不应混为一谈：

| 计算     | 用途                                   | 上游实现              |
| -------- | -------------------------------------- | --------------------- |
| 欢愉伤害 | 计算一次欢愉伤害的期望值               | `damageCalculator.ts` |
| 阿哈速度 | 根据欢愉队友的战斗速度计算阿哈速度     | `ahaCalculations.ts`  |
| 角色速度 | 汇总角色基础速度、速度百分比和固定速度 | `calculateStats.ts`   |

上游优化器以预定义技能轮次计算伤害和评分，**不是完整行动轴模拟器**。它没有在这一计算链中统一使用 `10000 / SPD` 模拟整场行动值、拉条、能量循环和每次出手顺序。

## 2. 数值与单位约定

实现前必须统一以下口径：

- 百分比在计算层使用小数：`20%` 输入为 `0.20`。
- 速度和笑点使用实际数值，例如速度 `160`、笑点 `100`。
- 所有中间结果保留浮点精度，只在 UI 展示层格式化或四舍五入。
- 敌人等级、抗性、防御穿透等战斗参数必须显式传入，不能藏在 UI 组件默认值里。
- 角色技能倍率由角色配置提供；通用公式不负责猜测角色、技能等级或星魂状态。

建议计算层使用英文键名，与现有导入数据和类型保持一致；UI 再映射为中文：

| 中文     | 建议字段         | 单位 |
| -------- | ---------------- | ---- |
| 欢愉度   | `elation`        | 小数 |
| 热闹乘区 | `merrymaking`    | 小数 |
| 笑点     | `punchline`      | 点数 |
| 欢愉倍率 | `elationScaling` | 小数 |
| 防御穿透 | `defPen`         | 小数 |
| 抗性穿透 | `resPen`         | 小数 |
| 易伤     | `vulnerability`  | 小数 |
| 暴击率   | `critRate`       | 小数 |
| 暴击伤害 | `critDmg`        | 小数 |

`merrymaking` 的最终中文名应以对应游戏版本的正式文本为准；在确认前不要将它并入普通增伤或欢愉度。

## 3. 欢愉伤害公式

### 3.1 总公式

上游源码：

- [CPU 计算实现](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/optimization/engine/damage/damageCalculator.ts#L819-L852)
- [GPU/WGSL 等价实现](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/optimization/engine/damage/damageCalculator.ts#L853-L906)

```text
ElationDamage =
  7535.107
  × elationScaling
  × elationMulti
  × merrymakingMulti
  × punchlineMulti
  × brokenMulti
  × defMulti
  × resMulti
  × vulnerabilityMulti
  × finalDmgMulti
  × critMulti
  × trueDmgMulti
```

`7535.107` 是上游采用的 **80 级欢愉基础伤害常量**。

### 3.2 欢愉度乘区

```text
effectiveElation = max(elation, minElationOverride)
elationMulti = 1 + effectiveElation
```

- 一般情况下 `minElationOverride = 0`。
- 若技能机制规定本次伤害至少按某个欢愉度计算，则使用两者较大值。
- 不要把欢愉度加入普通元素增伤。

### 3.3 热闹乘区

```text
merrymakingMulti = 1 + merrymaking
```

这是独立乘区。除非后续正式数据明确改变口径，否则不能与 `elation` 或普通 `DMG Boost` 相加。

### 3.4 笑点乘区

设当前笑点为 `P`：

```text
punchlineMulti = 1 + (5 × P) / (P + 240)
```

参考值：

| 笑点 P | 笑点乘区 |
| -----: | -------: |
|      0 |   1.0000 |
|     60 |   2.0000 |
|    120 |   2.6667 |
|    240 |   3.5000 |
|    480 |   4.3333 |

公式在 `P = -240` 时无定义。产品输入应限制 `P >= 0`，而不是依靠计算函数容错负数。

### 3.5 弱点击破修正

```text
brokenMulti = enemyWeaknessBroken ? 1.0 : 0.9
```

这里判断的是敌人当前是否处于弱点击破状态，不是攻击属性是否命中弱点。

### 3.6 防御乘区

上游固定攻击方为 80 级，因此攻击方等级常量为 `80 + 20 = 100`：

```text
defMulti = 100 / ((enemyLevel + 20) × max(0, 1 - defPen) + 100)
```

注意：

- `defPen` 是本次伤害已汇总的有效防御穿透/无视防御。
- 上游通过 `max(0, 1 - defPen)` 将有效防御系数下限限制为 `0`，即超过 `100%` 的部分不会继续提高该乘区。
- 如果未来支持非 80 级角色，应把分子和末项 `100` 改为 `attackerLevel + 20`，不能继续硬编码。

### 3.7 抗性乘区

```text
effectiveResistance = clamp(enemyResistance - resPen, -1.00, 0.90)
resMulti = 1 - effectiveResistance
```

因此上游将有效抗性限制在 `-100%～90%`，对应抗性乘区 `2.0～0.1`。

### 3.8 易伤与最终伤害乘区

```text
vulnerabilityMulti = 1 + clamp(vulnerability, 0, 2.50)
finalDmgMulti = 1 + finalDmgBoost
```

- 易伤在上游被限制为 `0～250%`。
- `finalDmgBoost` 是独立的最终伤害修正，不应提前合并到易伤。

### 3.9 期望暴击乘区

上游计算的是平均期望伤害，不是“本次必定暴击”的伤害：

```text
effectiveCritRate = min(1, critRate + critRateBoost)
effectiveCritDmg = critDmg + critDmgBoost
critMulti = effectiveCritRate × (1 + effectiveCritDmg)
          + (1 - effectiveCritRate)
```

等价简化为：

```text
critMulti = 1 + effectiveCritRate × effectiveCritDmg
```

建议本项目同时提供两种输出：

- `expectedDamage`：使用期望暴击乘区；
- `critDamage`：按 `1 + effectiveCritDmg` 计算必暴伤害。

若只实现一种，默认应与上游一致，使用 `expectedDamage`。

### 3.10 真实伤害修正

```text
trueDmgMulti = 1 + trueDmgModifier + hitTrueDmgModifier
```

`trueDmgModifier` 来自角色当前状态，`hitTrueDmgModifier` 来自具体伤害段定义。

### 3.11 明确不参与的乘区

上游源码明确规定：**欢愉伤害不受普通 DMG Boost 和元素伤害加成影响**。

因此以下属性不能直接乘入本公式：

- 普通“造成的伤害提高”；
- 物理、火、冰、雷、风、量子、虚数属性伤害提高；
- 只限定普攻、战技、终结技等类型，且没有命中欢愉伤害标签的增伤。

但以下效果仍可能参与：

- 明确限定欢愉伤害的易伤或穿透；
- 防御和抗性相关效果；
- 暴击率、暴击伤害；
- 最终伤害、真实伤害修正；
- 具体技能定义中的最低欢愉度或额外倍率。

## 4. 阿哈速度公式

### 4.1 正向计算

上游实现与反向求解：[ahaCalculations.ts](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/tabs/tabCalculators/ahaCalculations.ts#L1-L31)。

首先将欢愉队友的**战斗速度**从高到低排序：

```text
s1 >= s2 >= s3 >= s4
```

然后计算：

```text
AhaSpeed = 80 + s1 / 5 + s2 / 10 + s3 / 20 + s4 / 40
```

通用权重表达式：

```text
weight(rank) = 1 / (5 × 2^min(rank, 3))
```

其中代码的 `rank` 从 `0` 开始，所以前四名权重依次为 `1/5、1/10、1/20、1/40`。

示例：队伍战斗速度为 `200、160、140、100`：

```text
AhaSpeed = 80 + 200/5 + 160/10 + 140/20 + 100/40
         = 145.5
```

### 4.2 输入必须是战斗速度

公式输入是队友的最终战斗速度，而不只是角色面板基础速度。后续 UI 应明确标注“战斗速度”，避免用户漏算：

- 角色/光锥/遗器提供的速度百分比；
- 固定速度；
- 当前计算场景中已启用的战斗内速度 buff。

对于有持续时间或触发条件的速度效果，计算器只能表示指定快照。UI 应提示用户选择或手动输入目标状态下的速度。

### 4.3 排序是公式的一部分

队友速度不是按编队位置分配权重，而是每次计算前降序排列。任一队友速度变化并跨过另一名队友时，两人的权重也会交换。

因此不能简单地为四个固定槽位长期绑定 `1/5、1/10、1/20、1/40`；计算函数必须先复制并排序输入，且不得修改调用者原数组。

### 4.4 人数边界

- 无队友输入时，阿哈速度为基础值 `80`。
- 正常队伍最多按四名欢愉队友处理。
- 上游底层权重函数会让第五名及之后继续使用 `1/40`，但这是函数的防御性行为，不应被解释为游戏支持超过四名队友。
- 本项目产品层应限制输入数组长度为 `0～4`。

### 4.5 反向求解目标速度

需求形式：已知目标阿哈速度和若干队友速度，求新增一名队友至少需要的速度。

由于新速度可能插入排序后的任意位置，不能固定用某一个权重直接反推。上游算法为：

1. 将已有速度降序排列；
2. 从可能的最低插入位置向前检查；
3. 假设新增速度处于该排名，重新分配其后成员的权重；
4. 用剩余速度贡献除以新增位置的权重；
5. 选择与该排序位置一致的解。

特殊情况：没有已有队友时：

```text
requiredSpeed = (targetAhaSpeed - 80) / (1/5)
              = 5 × (targetAhaSpeed - 80)
```

当当前阿哈速度已经达到目标时，产品层应显示“目标已达到”，而不是把负速度作为推荐结果。

## 5. 普通角色速度公式

上游基础属性实现：[calculateStats.ts](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/optimization/calculateStats.ts#L84-L94) 和 [`sumFlatStat`](https://github.com/fribbels/hsr-optimizer/blob/d28928b1f09d7613c37ca7ca373a468367060fc0/src/lib/optimization/calculateStats.ts#L350-L360)。

站街速度的核心口径为：

```text
SPD = baseSPD × (1 + setSPD% + relicSPD% + traceSPD% + lightConeSPD%)
    + relicFlatSPD
    + traceFlatSPD
```

战斗内新增速度百分比通常仍以角色基础速度为基数：

```text
combatSPD = standingSPD
          + baseSPD × combatSPD%
          + combatFlatSPD
```

注意：

- 固定速度不再参与速度百分比乘算；
- 百分比速度以角色 `baseSPD` 为基数，不以当前总速度为基数；
- 不要在每个来源汇总时单独取整；
- UI 可展示一位小数，但速度断点判断应使用未格式化的实际值；
- 具体角色的速度继承、忆灵速度、基于他人速度的转换属于角色机制，应在通用速度汇总之后单独处理。

## 6. 与行动值的关系

常见的基础行动值表达式是：

```text
ActionValue = 10000 / SPD
```

但该表达式**不等于**上游已经实现完整行动轴模拟。行动提前、行动延后、额外回合、速度 buff 生效时点和轮次边界都会改变实际行动轴。

因此本项目后续若只做欢愉/阿哈速度计算器：

- 可以展示静态 `10000 / SPD` 作为参考；
- 不应声称能够预测完整出手顺序或零轮表现；
- 不应使用静态行动值替代技能轮次模拟。

若未来开发行动轴功能，应另写设计文档定义时间轴、状态持续时间和行动提前结算顺序。

## 7. 建议的本项目实现结构

公式属于无 UI 状态的纯计算逻辑，不能埋在 Vue SFC 中。按照本项目[架构设计](./架构设计.md)和[代码规范](./代码规范.md)，建议结构如下：

```text
src/shared/utils/elation/
├── constants.ts          # 7535.107、80 等通用常量及来源说明
├── damage.ts             # 欢愉伤害与各乘区纯函数
├── speed.ts              # 普通速度、阿哈速度、反向求解
├── types.ts              # 输入输出契约
└── *.test.ts             # Vitest 边界和回归测试

src/features/elation-calculator/
├── ElationCalculator.vue # 表单与结果展示
└── ...                   # 仅保存该功能的 UI/局部状态
```

依赖方向：

```text
page -> elation-calculator feature -> shared/utils/elation
```

实现原则：

1. 计算函数保持纯函数，不读取 Pinia、DOM 或 Tauri API。
2. 通用公式与角色倍率分离；角色倍率从角色数据或明确的技能配置传入。
3. 常量必须附带来源提交和数据版本，方便未来复核。
4. 输入校验放在公开计算入口；UI 校验用于即时提示，但不能成为唯一防线。
5. 计算结果同时返回总伤害和各乘区明细，便于 UI 解释结果和排查版本差异。
6. 如果功能需要持久化方案，再通过 `src/shared/api/<domain>.ts` 接入 Tauri；纯计算器不需要后端。

建议输出结构：

```ts
interface ElationDamageResult {
  damage: number;
  factors: {
    baseDamage: number;
    elationScaling: number;
    elationMulti: number;
    merrymakingMulti: number;
    punchlineMulti: number;
    brokenMulti: number;
    defMulti: number;
    resMulti: number;
    vulnerabilityMulti: number;
    finalDmgMulti: number;
    critMulti: number;
    trueDmgMulti: number;
  };
}
```

## 8. 最低测试清单

### 8.1 阿哈速度

| 场景     | 输入                   |     期望 |
| -------- | ---------------------- | -------: |
| 无队友   | `[]`                   |     `80` |
| 单队友   | `[200]`                |    `120` |
| 双队友   | `[200, 100]`           |    `130` |
| 自动排序 | `[100, 200]`           |    `130` |
| 四队友   | `[200, 160, 140, 100]` |  `145.5` |
| 同速度   | `[150, 150, 150, 150]` | `136.25` |

另外必须验证：

- 不修改输入数组；
- 拒绝负速度、非有限数和超过四名成员；
- 反向求解后把结果放回数组，正向计算应达到目标；
- 当前值已达目标时不返回负推荐速度；
- 新成员跨越已有成员排名时正确重排权重。

### 8.2 笑点乘区

```text
P = 0   -> 1
P = 60  -> 2
P = 120 -> 2.666666...
P = 240 -> 3.5
```

必须拒绝负数、`NaN` 和无穷大。

### 8.3 欢愉伤害

至少覆盖：

- 所有增益为零、敌人已击破时的基础结果；
- 未击破时结果恰为已击破结果的 `0.9`；
- `minElationOverride` 高于和低于当前欢愉度两种情况；
- 暴击率达到或超过 `100%` 时正确封顶；
- 防御穿透超过 `100%` 时防御系数不继续下降；
- 抗性在 `-100%` 和 `90%` 两端正确限制；
- 易伤超过 `250%` 时正确限制；
- 普通/元素增伤变化不会影响欢愉伤害；
- CPU 实现与将来可能增加的 Rust/WGSL 实现在固定夹具上结果一致。

### 8.4 普通速度

至少覆盖：

- 只有基础速度；
- 固定速度与百分比速度同时存在；
- 固定速度不被百分比二次放大；
- 多来源速度百分比先相加再乘基础速度；
- 显示值相同但内部小数不同的速度断点判断。

## 9. 暂不包含的功能

本文不定义以下内容：

- 每个欢愉角色的具体技能倍率和技能轮次；
- 光锥、遗器、星魂和队友条件的完整状态机；
- 全战斗行动轴、拉条和轮次模拟；
- 游戏版本之间的数据迁移策略；
- UI 视觉稿与交互细节。

这些能力可复用本文的纯公式，但需要各自的角色配置、状态模型或专项设计文档。

## 11. 一句话实现口径

> 欢愉伤害使用独立基础伤害和欢愉/笑点乘区，不吃普通与元素增伤；阿哈速度按欢愉队友战斗速度降序后，以 `1/5、1/10、1/20、1/40` 加权到基础速度 `80`；所有公式保持浮点精度并与角色机制、UI 状态分离。
